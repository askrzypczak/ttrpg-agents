# @ttrpg-agents/engine

The domain engine: dice, monster schema and search, encounter events, map geometry, and the table port. It has no Node built-ins and imports no other workspace package; the build (`types: []`) and `eslint.config.js` enforce that.

## Monsters

- `src/monsters/types.ts`: the `MonsterIndex` read port (`get`, `list`, `aliases`, `dndBeyondPage`), the built-in `MonsterSet`, and `staticMonsterIndex(set)`, which serves a set through the port.
- `src/monsters/creatures.ts`: the `CreatureRepository` driven port (the creatures the DM stored, one record per key, statblocks not validated by the store) and `createMonsterIndex(builtIn, creatures)`, which serves the built-in set and the stored creatures, reading the repository on every call. Built-in keys win. A stored record that fails `monsterSchema` is skipped, absent from `get` and `list` and so from search; a schema change migrates the rows, so this is only a safety net.
- `src/monsters/schema.ts`: zod schema and the `Monster` type, whose `source` is `{ book, page? }` (a lower-case book tag, such as the SRD's `srd-5.2`).
- `src/monsters/search.ts`: `searchMonsters(index, query)` (case-insensitive, plural-tolerant, ranked; also matches aliases, marked as alias hits; on a tie a stored creature ranks before a built-in monster) and `getMonsterByKey`.
- `src/monsters/dndbeyond.ts`: `dndBeyondUrl(index, monster)`, the monster's D&D Beyond 2024 page URL from `MonsterIndex.dndBeyondPage(key)`, or undefined when it has none.
- `src/monsters/footprint.ts`: `footprintForSize(size)`, the grid cells per side a token of a size category spans (small and medium 1, large 2, huge 3, gargantuan 4, anything else 1). `addMonsters` stores it on each new instance as `footprint`.
- `src/monsters/check.ts`: `checkMonster(monster)` reads a statblock's entries and checks its numbers. It returns a report per entry (the attack, the saving throws, the spell save DC and spell attack bonus, every dice expression, and whether the entry rolls; Multiattack never does) and findings, which are warnings that carry the printed value and every value the engine accepts: `damage_average`, `attack_bonus`, `save_dc`, `spell_save_dc`, `spell_attack_bonus`, `save_modifier` and `initiative`. It reads the 2024 wording; other wording stays text, so only its dice are listed and only its printed dice averages are checked. The proficiency bonus comes from the challenge rating (`proficiency.ts`). It is pure and never throws on entry text.
- `src/monsters/creature-changes.ts`: `creatureChangesSchema`, the partial statblock a creature tool changes (scalars replace; `hp` without `average` gets the dice's average; abilities, saves, speeds, senses and skills merge by key, `null` removing one; damage and condition lists replace; each section takes `remove`, `replace` and `add`, by entry name ignoring case, in that order), and the engine-internal rules for applying it, validating the result, minting the key (`<book>_<slug of name>`) and refusing a name the book already has.
- `src/monsters/create-creature.ts`: `createCreature(deps, request, origin)` builds a statblock from scratch or from a copy of any monster, checks the book tag (`monsterSchema`'s pattern, not reserved), validates it, refuses a name or key the book already holds, stores it and notes the command on the current encounter in one transaction, then returns it with `checkMonster`'s report. Findings never block.
- `src/monsters/stored-creatures.ts`: `editCreature` applies the same changes (plus `page`) to a stored creature under its key and book, refusing a built-in key and a name another creature of the book has, and returns the live instances of the key, which keep their copied values; `removeCreature` deletes a stored creature by key, refused while a live instance in any encounter uses it; both note the command on the current encounter in one transaction. `listCreatures` lists the stored creatures, of one book when given, by key.

## Encounter events

`src/encounter/types.ts` (`monsterInstanceSchema`) and `src/encounter/events.ts` (`encounterEventSchema`) are the source of truth for `MonsterInstance` and `EncounterEvent`; the protocol package reuses them as its wire payloads.

`src/encounter/origin.ts` (`changeOriginSchema`, `ChangeOrigin`): who made a change, `{source: "mcp" | "table", commandId}`. Every `EncounterRepository` mutation takes one as its last argument.

Each event carries the `origin` of the mutation that caused it. `instance-changed` covers rename, initiative, initiative group (`groupId`), armor class and stats visibility, and carries only the fields that the mutation set. The store records every mutation's event in an ordered log readable through `EncounterLog` (`src/encounter/log.ts`); the bridge polls it and broadcasts each event as an `encounter-event` with its `seq`, and sends an `encounter-snapshot` carrying the `seq` it is current as of after each `hello-ack`.

Each instance carries `spawnPosition`: where a new token for it is created, in scene units, or null for the extension's default row; rows, events and snapshots from before it read as null.

`src/encounter/hp.ts`: the rules behind absolute HP and armor class, which the store calls: `clampHp` (current HP kept within 0..max HP), `resizeMaxHp` (max HP raised to at least 1, current HP lowered to it when above, never raised) and `clampArmorClass` (raised to at least 0). Non-integers throw `InvalidAmountError`, or `InvalidArmorClassError` for armor class.

## Test data

`@ttrpg-agents/engine/testing` (`src/testing/index.ts`) exports `makeTestInstance`, a full `MonsterInstance` for tests, `makeTestMonsterIndex`, a `MonsterIndex` over given monsters, aliases and D&D Beyond pages, `makeTestMonster`, a full invented statblock that passes `monsterSchema` with no check findings, `makeTestCreatureRepository`, an in-memory `CreatureRepository` whose `put` stores any data, `pngDeclaring` and `webpDeclaring`, image headers declaring a size, `makeTestImageSource`, an `ImageSource` over given bytes by path or URL that records its loads, `makeTestTokeniser`, a `Tokeniser` that records its renders and answers a 512 px square WebP header, and `makeTestTooManyTokensIndex`, a TooManyTokens index with the given folders (none by default). It is test data only; production code must not import it (lint-enforced).

## Map

`src/map/`: pure geometry for placing monsters in rooms (image px <-> scene units <-> grid cells).

- Model (`transform.ts`): `scene = position + R(rotation) * (diag(scale) * k * (imagePx - imageOffset))`, `k = sceneDpi / imageDpi`, rotation in degrees clockwise about `position` (y down). Pixels are scaled as `(p * sceneDpi) / imageDpi` so exact corners hold. Multiples of 90 degrees use exact sine and cosine (`Math.cos(270deg)` is -1.8e-16 and would push a boundary point into the neighbouring cell).
- Cells (`cells.ts`): `sceneToCell` floors per axis (a point on a cell line is in the cell it starts); `cellCenter` is `(c + 0.5) * dpi`.
- Display grid (`display-grid.ts`): origin is the scene cell holding the map's top-left bounds corner; `cols`/`rows` are `round(boundsSize / sceneDpi)`. Labels are spreadsheet-style (`A1`, `Z10`, `AA1`; case-insensitive on parse), ranges are `T5:AB11` (a single cell `T5` is 1x1, reversed corners are normalised). Bad labels or ranges throw `InvalidCellRangeError`. `cellRangeToPolygon` and `polygonToCellRange` convert between a range and an image-px polygon; the latter returns the smallest range holding every cell centre inside the polygon, or `undefined`. `formatColumnLabel(col)` gives the column letters alone (`A`, `AF`).
- Polygons (`polygon.ts`, `rooms.ts`): a point on an edge or vertex is inside, with a tiny float tolerance. A `Room` is a name plus polygons in image px; `findRoom` ignores case and `UnknownRoomError` lists the known rooms.
- Picker (`picker.ts`): `pickFreeCells` picks non-overlapping footprint x footprint blocks whose cells all have their centre inside the room and none is occupied. It starts at the block whose centre is nearest the mean of all the room's cell centres, then farthest-point sampling between block centres; ties go to the first block in scene order (rows, then columns, of its top-left cell). When that spread fits fewer blocks than asked, it packs the room in scene order (first fit) instead if that fits more. Each pick gives its cells and its centre (a grid intersection for an even footprint).
- Registration (`repository.ts`, `use-map.ts`): `MapRegistration` is a map item's id, name and `MapPlacement`. The `MapRepository` port (driven) belongs to one encounter (`EncounterDirectory.mapRepositoryFor`): it stores registrations by item id and records its encounter's map; registering an item again replaces its earlier registration. Rooms are keyed by map item, so encounters on one map share them. `useMap(table, maps, name?)` reads `sceneMap()` and registers the map: a grid that is not `SQUARE` fails with `UnsupportedGridError`; without a name the scene must have exactly one map, and with a name it takes the one map whose name matches ignoring case. Every other choice fails with `MapSelectionError`, and its message lists the maps' names; so does a map that covers less than one grid cell. Nothing is stored on failure; on success it returns the registration and the display grid's `cols` and `rows`.
- Placement (`place-monsters.ts`): `addMonstersInRooms` checks the groups, the map in use and the room names, reads `sceneMap` and `sceneTokens`, marks every cell whose centre lies inside or on the edge of a token's bounds as occupied, picks free blocks of each group's footprint (from its monster's size) with `pickFreeCells`, largest footprint first and ties in input order (each group's picks are occupied for the next), and adds the monsters in input order with their spawn positions (the block centres); monsters that do not fit get none. The result gives each placed monster's display cell, or its block's display range ("A1:B2") for a footprint above 1, and says whether the map moved. Without a room it adds like `addMonsters` and does not ask the table. With `defaultArt` the groups' types' default art loads after those checks and before the table reads, and is written before the add in one transaction.
- Proposals and map image (`room-index.ts`, `map-image.ts`): `proposeRooms(rooms)` checks names and ranges like `setRooms` and returns each range shrunk by one cell on every side where it spans three or more cells (a proposal; nothing is read or stored). `getMapImage(table, maps)` reads the active map's live placement like `listRooms`, then asks `mapImage` for its gridded image, and returns it with the display grid's `cols` and `rows` and whether the map moved.

## Table

`src/table/`: `TablePort` (driven port: `sceneStatus()` asks the table, the VTT, about its scene; `sceneMap()` asks for the scene grid and the map images with their transforms; `sceneTokens()` asks for the position of each item on the table's character and mount layers, which the room placement for `add_monsters` (#50) reads to skip occupied cells; `mapImage(itemId)` asks for the gridded image of a map item, drawn as the DM sees it with the display grid's labels; all fail with `TableUnavailableError`). The bridge client implements the port.

`getTableStatus(directory, table)` asks the table, then compares its answer with the open scene's bound encounter read from the store (it creates and resolves none): `inSync` = scene ready, the tab holds that encounter for that scene, and token, applied and encounter counts all equal, with no art picker open or still to open. Our tokens of another encounter or none are counted apart (`unmanagedTokenCount`) and do not affect sync. With no scene open there is nothing to compare: the tab cannot hold it and the encounter count is 0. An older tab, whose answer has no scene id or held encounter, keeps the count checks alone (`holdsOpenScene` undefined). `mcp` only formats the result.

## Browser

`src/browser.ts`: `BrowserPort` (driven port: `showPage(url)` shows a page to the DM in their browser, and rejects with the reason when it cannot), implemented in `mcp` (`src/system-browser.ts`).

## Tokens

The engine owns the crop maths, the limits and the token style; `@ttrpg-agents/imaging` implements the ports below.

- `src/encounter/image-source.ts`: the `ImageSource` driven port (`load(location)` answers a source image's bytes, or rejects with `ImageUnavailableError` naming the path or URL and the cause), `IMAGE_LOAD_TIMEOUT_MS` (5 s) and `parseImageLocation(image)`: an `https://` URL is a url and a string starting with `/` a path; an `http:` URL, another scheme, a relative or an empty path throw `InvalidTokenRequestError`.
- `src/encounter/tokeniser.ts`: the `Tokeniser` driven port (`focalPoint(bytes)`, the image's most salient point as fractions of its width and height, and `renderToken(bytes, crop, style)`; both reject with `TokeniserError`), `TOKEN_STYLE` (a 512 px square with a `#6e4b2a` ring 0.03 of the side wide) and `TOKEN_ZOOM_MAX` (8).
- `tokenCrop(size, { focus, zoom })`: the square, in source pixels, whose side is the shorter side divided by the zoom (at least 1 px), centred on the focus and moved inside the image where it would cross an edge. A zoom outside 1 to 8 or a focus outside 0 to 1 throws `InvalidTokenRequestError`. Crops are in the stored pixel grid: EXIF orientation is ignored.
- `makeToken(deps, image, { focus?, zoom? })` checks the focus and zoom before loading anything, loads the image, refuses a source that `validateTokenSource` refuses (PNG, JPEG or WebP, at most 20 MiB and 8,192 px a side) with `ImageUnavailableError`, crops at the focus (default: the tokeniser's focal point) and zoom (default 1), and renders with `TOKEN_STYLE`. An output that fails `validateTokenImage` or is not a 512 px square WebP is a `TokeniserError`. It stores nothing.
- `src/encounter/own-token-art.ts`: `setOwnTokenArt(deps, monsterKey, image, { focus?, zoom? }, origin)` makes a token, stores its bytes and sets them as the monster type's art with source `agent` in one transaction, replacing any art and noting the command on the current encounter. The art has no url until the GM publishes it. A token whose hash the type's art already has keeps that art and writes nothing. An unknown monster key throws `UnknownMonsterError` before anything loads.
- `src/encounter/default-art.ts`: the TooManyTokens default for a monster type with no art, in two phases. `loadDefaultArt` writes nothing: per distinct key it answers `has-art` (any stored art), `not-covered` (no default variant), or loads the default variant from jsDelivr, else raw.githubusercontent.com, keeping the first url whose bytes pass `validateTokenImage`; both failing is `failed` with each try's reason. Only `ImageUnavailableError` counts as a failed load. `storeDefaultArt` then, in one art transaction, stores each loaded type's bytes, sets its art (url, mime, size, hash) with source `default` unless the type got art meanwhile, and runs the use case's write. `changeMonsterTypeWithDefaultArt`, `restoreMonstersWithDefaultArt` and `restoreEncounterWithDefaultArt` run their use case's checks, then the load, then the art and the use case in one transaction, art first; a failed load never fails the call.
- `src/setup/port.ts`: the `TokeniserProbe` driven port (`check()`, never rejects). The setup report's last row is the tokeniser: ok when its image library loaded, else a problem with the reason and the `reinstall-dependencies` fix.
